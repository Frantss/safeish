## Before acting

- Read until the pattern is clear. Find how this repo handles the task and match
  it. Add a convention when the task needs one.
- Ask when local evidence cannot resolve an uncertainty whose answers would
  change the work. Offer two concrete options when the user must decide.

## Deciding vs. asking

- Proceed with small, reversible changes. Ask before architectural,
  cross-cutting, or hard-to-reverse changes. Any change to the public API
  (exported names, signatures, the `SafeishResult` / `SafeishError` shapes, the
  `~unhandled` code) is hard to reverse once published.
- Resolve harmless ambiguity with the best interpretation. State the assumption
  and continue.
- Treat branches, installs, deletions, and servers as side effects.
  Proceed when the request implies a necessary, reversible action. Ask for
  consent in other cases. Publishing (`pnpm release`, `npx jsr publish`) is
  irreversible: run it only on an explicit request.

## Proposing solutions

- For a consequential decision, present the viable options and their trade-offs.
  Recommend one and explain why you rejected the closest alternative.
- Use the clear path when one path fits the task.

## Scope

- Do the requested work and nothing adjacent.
- Report unrelated bugs, dead code, and poor patterns. Leave their source
  unchanged.
- Finish the in-scope work. Name each incomplete part and its exact blocker.

## Terminology

- **Result**: the success value, `{ ok: true, data }`, built with `result`.
- **Error**: the failure value, `{ ok: false, error: { code, context, message } }`,
  built with `error` or an error definition.
- **Error definition**: the builder returned by `defineError`; carries `code`,
  `message`, optional `effect`, and the type-only `$context`.
- **Unhandled**: the error `safeish` returns when the wrapped function throws;
  code `~unhandled` unless a custom definition is passed.

## Documentation

- `readme.md` is the package's public documentation on npm and JSR. Update its
  Usage and API sections in the same change as any public API change, and keep
  its examples compiling against the current exports. Leave out
  implementation details and changelogs.
- JSDoc on exported functions is user-facing (shown in editors and on JSR). Keep
  it accurate to the signature when changing a public function.
- `CHANGELOG.md` is generated by changesets. Edit it only through a changeset.

## Writing code

- The public surface is the single entry point `entries/index.ts`, which
  re-exports `src/`. A new entry point also needs `package.json` `exports`,
  `jsr.json` `exports`, and `tsdown.config.ts` `entry`.
- Import across modules with the `~/src/*` and `~/entries/*` aliases.
- Public types use the `Safeish` prefix and live in `src/types.ts`.
- Tests live in `test/*.spec.ts` and import through the entry points, as users
  would. Typecheck is on: assert inferred types with `assertType` alongside
  runtime assertions, since the inferred error-code union is the product.

## Done

- Run checks proportional to the change and report their exact outcome:
  - `pnpm lint` (Biome; `pnpm lint:fix` to format).
  - `pnpm vitest run` — `pnpm test` starts watch mode in a terminal. CI does
    not run tests, so run them locally.
  - `pnpm build && pnpm check-exports` for changes to entries, exports, or
    build config.
- A user-facing change needs a changeset (`pnpm changeset`) choosing the semver
  bump. Changesets does not bump `jsr.json`; keep its `version` equal to
  `package.json` when versioning.
- Include failure output and name skipped checks. Separate verified behavior
  from assumptions.
- Review each modified file before handing work back.

## Git

- Never commit unless the user explicitly asks to commit the current work. A
  prior request does not authorize commits for later work.
- When asked to commit, partition the requested work into atomic commits. Give
  each one an intent and include its implementation, tests, documentation,
  changeset, and configuration. Leave the repo building with scoped checks
  passing.
- For each requested commit, stage exact paths or hunks, review
  `git diff --cached`, and run checks covering the staged change. Keep unrelated
  or user-owned changes separate.
- Use a conventional prefix and lowercase subject for requested commits, such
  as `feat:`, `fix:`, `docs:`, or `test:`. Add a body when context is needed.
- Use descriptive, hyphenated branch names without a `feature/` prefix.
- Check the branch, remotes, and upstream before claiming that work has a
  backup. Treat untracked files as unbacked.

## Communication

- Write terse, technical responses. Skip preambles, request summaries, and
  praise.
- Explain hard decisions. State obvious outcomes without commentary.
- If you disagree, say so once in one or two sentences, then follow a repeated
  instruction.
- Say “I don't know” instead of presenting a guess as fact.
